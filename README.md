# QA Toolkit

금전성 데이터를 다루는 서비스의 QA를 위해 만든 도구 세 개입니다.

| 도구 | 하는 일 | 실행 |
|---|---|---|
| **recon** 정합성 대사 | 건 단위 로그와 묶음 단위 집계를 같은 시간 창으로 대조하고, 창 경계 때문에 생기는 차이를 정확히 분리한 뒤 설명되지 않는 차이만 결함 후보로 뽑습니다 | `python -m recon check ...` |
| **gate** 릴리즈 품질 게이트 | TC 결과와 미해결 결함 목록을 읽어 심각도 × 우선순위 매트릭스와 통과율 기준으로 GO / CONDITIONAL GO / NO-GO를 판정합니다 | `python -m gate ...` |
| **apiqa** API 테스트 하네스 | 메시지 플랫폼 API를 직접 호출해 인증, 권한, 응답 계약, 경계값, 멱등성, 페이지 조회, 동시성을 검증합니다. 서버에 결함을 심어 하네스가 잡는지도 확인합니다 | `python tools/api_fault_check.py` |

모든 데이터는 생성기로 새로 만든 가짜 데이터입니다. 실제 회사 데이터나 내부 문서는 쓰지 않았고, 테이블 구조와 기록 방식만 실무에서 다룬 것과 같은 성격으로 재현했습니다.

---

## 1. 왜 만들었나

게임 QA를 할 때 Common DB(플레이 시점 기록)와 Shard DB(세션 단위 기록)의 재화 합계를 빌드마다 쿼리로 뽑아 엑셀에서 대조했습니다. 3시간 단위로 비교하면 세션 경계에 걸친 기록이 한쪽에만 잡혀서 정상인데도 차이가 크게 났고, 그래서 창을 3일로 넓혀 경계 효과를 줄인 뒤 남은 차이가 세션 잔여분 수준인지 보고 정상 판정을 했습니다.

이 방식에는 두 가지 한계가 있었습니다.

1. 창을 넓히면 차이가 줄어들 뿐 0이 되지는 않습니다. 남은 차이가 "잔여분 수준"이라는 판단은 결국 사람의 감입니다. 작은 결함이 그 잔여분 안에 숨을 수 있습니다.
2. 빌드마다 쿼리와 대조를 손으로 반복했습니다.

recon은 경계 효과를 세션 단위로 정확히 계산해서 뺍니다. 그래서 어떤 창 크기로 잘라도 정상 데이터의 미설명 차이는 정확히 0이고, 0이 아니면 그 금액이 어느 세션의 어떤 문제인지까지 바로 나옵니다.

## 2. 결과 요약

`python run_demo.py` 실행 결과 (스핀 20만 건, 세션 3천 개, 결제 승인 2만 5천 건)

**정상 데이터에서 창 크기별 원시 차이** (베팅 합계 기준)

| 창 크기 | 원시 차이 평균 | 최대 | 경계 효과를 뺀 미설명 금액 |
|---|---:|---:|---:|
| 1시간 | 28.78% | 120.05% | 0 |
| 3시간 | 7.12% | 24.75% | 0 |
| 1일 | 2.12% | 2.88% | 0 |
| 3일 | 0.14% | 0.14% | 0 |

실무에서 3시간 창이 쓸 수 없을 만큼 흔들렸던 이유와, 3일로 넓혔을 때 차이가 작아졌던 이유가 그대로 재현됩니다. 그리고 엔진으로 경계 효과를 빼면 모든 창 크기에서 0이 됩니다.

**결함을 심은 데이터**

| 시나리오 | 심은 결함 | 검출 | 오탐 |
|---|---:|---:|---:|
| 게임 재화 (3일 창) | 10 | 10 | 0 |
| 결제 승인 vs 정산 (일별 창) | 5 | 5 | 0 |

결함 주입 데이터에서 미설명 금액 합은 창 크기를 1시간으로 하든 3일로 하든 똑같이 -5,964,000원입니다. 창 크기는 결함을 찾는 데 영향을 주지 않습니다.

**테스트**: 104개 통과 (대사, 게이트 70개 + API 하네스 34개). 일부러 버그 9개를 심어 테스트가 잡는지 확인했고 9개 모두 잡혔습니다 (`python tools/mutation_check.py`). API 서버에 결함 7개를 심었을 때도 7개 모두 하네스가 잡았습니다 (`python tools/api_fault_check.py`).

## 3. 실행

Python 3.10 이상. 외부 라이브러리 없이 표준 라이브러리(sqlite3)만 씁니다. 테스트에만 pytest가 필요합니다.

```bash
pip install -r requirements.txt

python run_demo.py                 # 전체 데모. reports/report.html 생성
python -m pytest                   # 테스트 104개
python tools/mutation_check.py     # 테스트가 버그를 잡는지 확인
python tools/api_fault_check.py    # API 하네스가 서버 결함을 잡는지 확인
python tools/verify_files.py       # 받은 파일이 빠짐없이 그대로인지 확인
```


정상 동작 확인 기준

| 명령 | 이렇게 나오면 정상 |
|---|---|
| `python -m pytest` | `104 passed` |
| `python run_demo.py` | 게임 `10개 중 10개 검출, 오탐 0개`, 결제 `5개 중 5개 검출, 오탐 0개`, 게이트 샘플 A `GO` / B `CONDITIONAL GO` / C `NO-GO` |
| `python tools/mutation_check.py` | `심은 버그 9개 중 9개를 테스트가 잡음` |
| `python tools/api_fault_check.py` | `심은 서버 결함 7개 중 7개를 하네스가 잡음` |
| `python tools/verify_files.py` | `받은 파일이 전부 그대로 있습니다.` |

개별 실행

```bash
# 데이터 생성 (--inject 를 붙이면 결함을 심는다)
python -m recon generate --scenario game --db data/game.db --inject

# 3일 창 한 번에 대사
python -m recon check --scenario game --db data/game.db --start "2026-03-02" --end "2026-03-05" --csv reports/findings.csv

# 3시간 창으로 잘라서 대사
python -m recon check --scenario game --db data/game.db --start "2026-03-02" --end "2026-03-05" --step 3h

# 결제 시나리오
python -m recon generate --scenario payment --db data/pay.db --inject
python -m recon check --scenario payment --db data/pay.db --start "2026-03-02" --end "2026-03-05" --step 1d

# 릴리즈 게이트
python -m gate --results gate/samples/release_nogo/tc_results.csv --defects gate/samples/release_nogo/open_defects.csv
```

종료 코드로 파이프라인과 연결할 수 있습니다.

| | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| recon | 정상 | 주의 | 결함 후보 | 검증 불가 |
| gate | GO | CONDITIONAL GO | NO-GO | 입력 오류 |

`.github/workflows/qa-gate.yml`에 GitHub Actions 연결 예시가 있습니다.

## 4. recon 설계

### 핵심 등식

```
원시 차이 = 집계 합계 - 상세 합계

원시 차이 = (carried_in - carried_out)           <- 경계 효과, 설명되는 차이
          + 묶음 합계 불일치 (허용 오차 내 + 초과)
          - 마감 이후 기록
          - 집계 누락
```

- **carried_in**: 이번 창에 마감된 세션에 들어 있지만, 스핀 자체는 창 밖에서 일어난 금액
- **carried_out**: 이번 창에 일어났지만 세션이 아직 안 끝났거나 창 이후에 끝나는 금액

경계 효과를 빼고 남은 금액(미설명 차이)은 드릴다운으로 찾은 원인 금액의 합과 정확히 같아야 합니다. 엔진은 매번 이 등식을 스스로 확인하고, 안 맞으면 판정을 "검증 불가"로 냅니다. 도구가 뭔가를 놓쳤는데 정상이라고 말하는 상황을 막기 위해서입니다.

### 잡아내는 결함

| 구분 | 의미 | 실제로 생기는 상황 | 등급 |
|---|---|---|---|
| 합계 불일치 | 세션(배치) 합계 ≠ 그 세션에 속한 건의 합 | 재화 중복 지급, 로그 누락, 중복 매입, 취소 미반영, 수수료 오류 | FAIL |
| 집계 누락 | 건은 있는데 소속 세션(배치) 행이 없음 | 세션 종료 처리 실패, 배치 생성 누락 | FAIL |
| 마감 이후 기록 | 이미 마감된 세션에 늦게 찍힌 건 | 지연 적재, 서버 간 시각 불일치 | FAIL |
| 중복 적재 | 같은 건 ID가 두 번 이상 | 재시도 로직 중복 적재 | FAIL |
| 시간 역전 | 세션 기간 밖 시각으로 찍힌 건 (금액 영향 없음) | 시각 기록 오류 | WARN |

### 시나리오가 두 개인 이유

엔진은 테이블 이름을 직접 알지 않고 `recon/scenarios.py`의 매핑만 봅니다. 게임 재화의 "스핀 로그 vs 세션 집계"와 결제의 "승인 내역 vs 정산 배치"는 도메인은 달라도 구조가 같습니다. 건이 발생 시각에 기록되고, 묶음이 마감 시각에 합계로 기록됩니다. 그래서 같은 엔진이 그대로 돌아갑니다.

결제 쪽에는 실무에서 자주 부딪히는 문제를 하나 더 넣었습니다. 건별 수수료는 건마다 원 단위로 절사하고 배치 수수료는 합계에서 한 번 절사하면, 정상이어도 배치당 최대 (건수 - 1)원 차이가 납니다. 이건 결함이 아니라 정책 차이라서 지표별로 허용 오차를 따로 둡니다.

## 5. gate 설계

규칙은 코드가 아니라 `gate/rules.json`에 있습니다. 기준을 바꾸려면 파일만 고치면 되고, 기준이 바뀐 이력이 남습니다.

- 심각도 × 우선순위 매트릭스로 결함마다 출시 차단, 조건부, 출시 후 대응을 정합니다
- 조건부 결함은 수정 계획이 합의된 경우에만 조건부 출시, 아니면 차단입니다
- 결제, 재화, DB 정합성은 금전성 영역으로 묶어 통과율 100%, 수행 못 한 TC 0건을 요구하고 결함 심각도를 한 단계 올려서 봅니다
- 수정은 됐지만 재검증 전(Fixed)인 결함은 열린 것으로 봅니다
- 보류(Deferred) 처리해도 차단 기준에 해당하면 차단입니다. 담당자가 보류를 눌러 기준을 우회하지 못하게 하기 위해서입니다
- 실패 TC가 있는데 그 카테고리에 열린 결함이 없으면 리포팅 누락으로 봅니다
- 입력 파일이 잘못되면 (합계가 안 맞는 행, 모르는 심각도, 중복 ID 등) 판정을 내리지 않습니다

## 6. apiqa 설계

### 대상
`apiqa/server.py`는 테스트 대상으로 쓰는 연습용 메시지 플랫폼 서버입니다. 표준 라이브러리만으로 만들었고, 대화방 메시지 전송, 목록 페이지 조회, 단건 조회, 전송 취소 API를 제공합니다. `python -m apiqa serve --port 8080`으로 띄워 직접 호출해 볼 수 있습니다.

### 하네스
- `apiqa/client.py`의 ApiClient가 요청을 보내고 상태 코드, 헤더, 본문을 그대로 돌려줍니다. 오류 응답도 예외 없이 돌려줘서 테스트가 4xx를 그대로 검증할 수 있습니다
- `check_schema`가 응답이 계약(필드 이름과 타입)과 다른 점을 목록으로 돌려줍니다. 빠진 필드뿐 아니라 계약에 없는 필드가 생겨도 잡습니다
- 테스트마다 서버를 새로 띄워 상태가 섞이지 않게 했습니다

### 검증 항목 (`tests/test_api_contract.py`, 34개)

| 영역 | 확인하는 것 |
|---|---|
| 인증, 권한 | 토큰 없음, 잘못된 토큰 401. 대화방 멤버가 아니면 전송, 목록, 단건 조회 모두 403. 남의 메시지 취소 403 |
| 응답 계약 | 전송, 단건, 목록 응답의 필드와 타입. 전송한 내용과 조회한 내용이 같은지 |
| 입력 검증, 경계값 | 빈 문자열, 공백, 숫자, 필드 누락, 깨진 JSON 400. 정확히 1000자는 성공, 1001자는 실패. limit 0, 101, 문자 400 |
| 멱등성 | 같은 Idempotency-Key로 재전송하면 같은 메시지를 돌려주고 새로 만들지 않음. 키는 사용자별로 구분. 같은 키로 동시에 10번 보내도 1건 |
| 페이지 조회 | limit 1, 7, 25, 100에서 커서를 따라가면 25건이 빠짐없이, 중복 없이, 순서대로 나오고 마지막 커서는 null |
| 동시성 | 40건 동시 전송에서 순번이 겹치지 않음 |
| 전송 취소 | 취소하면 단건 410, 목록에서 빠짐. 두 번 취소하면 410 |

### 결함 주입 (`tools/api_fault_check.py`)
테스트가 통과했다는 것만으로는 하네스가 결함을 잡을 수 있는지 알 수 없어서, 서버에 결함을 하나씩 심어 띄우고 테스트가 실패하는지 확인합니다. 정상 서버에서 전부 통과하는지 먼저 확인한 뒤에 진행합니다.

| 심은 결함 | 잡은 테스트 |
|---|---|
| 같은 키 재전송을 새 메시지로 저장 | 멱등성 테스트 2개 |
| 다음 페이지 커서를 하나 건너뜀 | 페이지 조회 테스트 |
| 방 멤버가 아니어도 목록 조회 허용 | 권한 테스트 |
| 정확히 1000자를 거부 | 경계값 테스트 |
| 취소한 메시지가 목록에 남음 | 전송 취소 테스트 |
| 단건 응답에서 필드 하나 누락 | 응답 계약 테스트 |
| 순번 발급에 잠금이 없음 | 동시성 테스트 |

## 7. 검증 방법

| 테스트 | 무엇을 확인하나 |
|---|---|
| `test_recon_oracle.py` | 손으로 계산할 수 있는 작은 데이터로 carried_in, carried_out, 원시 차이를 정확한 숫자로 확인. 결함 유형마다 하나씩 심어서 정확히 그것만 잡히는지 확인 |
| `test_recon_generated.py` | 큰 데이터에서 정상이면 1시간 ~ 3일 어떤 창에서도 오탐 0건. 심은 결함은 시드 5개에서 정답지와 정확히 일치. 등식은 항상 성립 |
| `test_gate.py` | 매트릭스 12칸 전부, 경계값(통과율 정확히 95%), 상태별 처리, 입력 오류 8종 |
| `tools/mutation_check.py` | 코드에 버그를 일부러 심었을 때 테스트가 실패하는지 확인 |
| `test_api_contract.py` | 위 6장의 API 계약 34개 |
| `tools/api_fault_check.py` | 서버에 결함을 심었을 때 API 하네스가 실패하는지 확인 |

손계산 테스트를 따로 둔 이유: 생성기와 엔진을 같은 사람이 만들면 같은 착각을 공유할 수 있습니다. 생성기 데이터로만 테스트하면 둘이 같이 틀렸을 때 테스트가 통과해 버립니다.

- SQLite 기준입니다. 실제 MySQL 환경에서는 날짜 타입 비교, 인덱스, 대용량 분할 조회를 맞춰야 합니다
- 상세 로그에 소속 세션 ID(배치 ID)가 있다고 가정합니다. 없으면 시간 범위로 소속을 추정해야 해서 정확도가 떨어집니다
- 세션 테이블의 키 중복은 스키마(PRIMARY KEY)로 막아 두었습니다. 실제 환경에서 보장되지 않으면 별도 검사가 필요합니다
- gate는 TC와 결함이 ID로 연결돼 있지 않아서 결함 등록 누락을 카테고리 단위로만 확인합니다
- apiqa의 서버는 연습용입니다. 실제 서비스에 붙이려면 ApiClient의 주소와 토큰만 바꾸면 되지만, 테스트 데이터 준비와 정리 방식은 환경에 맞게 따로 만들어야 합니다
- 동시성 테스트는 타이밍에 의존합니다. 잠금 누락 결함을 5번 반복해 5번 모두 잡았지만, 환경에 따라 놓칠 가능성은 남아 있습니다
