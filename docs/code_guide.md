## 1. 30초 설명

> 게임 QA 때 두 DB의 재화 합계를 빌드마다 손으로 대조했습니다. 3시간 단위로 보면 세션 경계 때문에 정상이어도 차이가 크게 나서 3일로 넓혀 판단했는데, 그 판단이 결국 감이었습니다. 그래서 경계 때문에 생기는 차이를 세션 단위로 정확히 계산해서 빼는 도구를 만들었습니다. 정상이면 어떤 창 크기에서도 미설명 차이가 0이고, 0이 아니면 어느 세션의 무슨 문제인지 바로 나옵니다. 같은 엔진으로 결제 승인과 정산 배치 대사도 돌아갑니다. 거기에 릴리즈 판정 기준을 규칙 파일로 만든 게이트 도구를 붙였고, 둘 다 종료 코드로 배포 파이프라인에 연결할 수 있습니다.

## 2. 경계 효과를 숫자로 이해하기

이게 이 도구의 핵심입니다. `tests/test_recon_oracle.py`에 있는 7건짜리 데이터로 설명합니다.

분석 창은 10:00 ~ 13:00입니다.

| 세션 | 시작 | 마감 | 스핀 (시각, 베팅액) | 세션 합계 |
|---|---|---|---|---:|
| S1 | 09:00 | 10:30 | 09:10 (100), 10:10 (200) | 300 |
| S2 | 11:00 | 11:30 | 11:05 (50), 11:20 (50) | 100 |
| S3 | 12:30 | 13:30 | 12:40 (70), 13:10 (30) | 100 |
| S4 | 12:50 | 진행 중 | 12:55 (40) | 없음 |

**상세 합계** (스핀이 일어난 시각이 창 안인 것만): 10:10의 200 + S2의 100 + 12:40의 70 + 12:55의 40 = **410**

**집계 합계** (세션 마감 시각이 창 안인 것만): S1 300 + S2 100 = **400**

원시 차이 = 400 - 410 = **-10**. 정상 데이터인데 차이가 납니다. 이유는 두 가지입니다.

- **carried_in = 100**: S1은 창 안에서 마감돼서 집계에 들어갔는데, 그 안의 09:10 스핀은 창 밖에서 일어났습니다. 집계 쪽에만 있는 금액입니다.
- **carried_out = 110**: 12:40 스핀(70)은 창 안에서 일어났지만 S3이 13:30에 마감돼서 아직 집계에 없습니다. 12:55 스핀(40)은 S4가 아직 안 끝나서 집계에 없습니다. 상세 쪽에만 있는 금액입니다.

경계 효과 = carried_in - carried_out = 100 - 110 = -10

미설명 차이 = 원시 차이 - 경계 효과 = -10 - (-10) = **0**. 정상입니다.

실무에서 창을 3일로 넓혔던 건, 창이 커질수록 경계에 걸리는 세션 비율이 줄어서 이 -10 같은 값이 전체 대비 작아지기 때문이었습니다. 이 도구는 그 값을 정확히 계산해서 빼기 때문에 창 크기에 의존하지 않습니다.

## 3. 엔진이 하는 일 (`recon/engine.py`)

`Reconciler.check(start, end)` 하나가 핵심입니다. 쿼리 네 개로 합계를 구하고, 다섯 가지 드릴다운을 돌립니다.

### 합계 쿼리 4개

```sql
-- 1) 상세 합계: 발생 시각이 창 안인 건
SELECT SUM(bet_amount) FROM play_log WHERE played_at >= ? AND played_at < ?

-- 2) 집계 합계: 마감 시각이 창 안인 세션
SELECT SUM(total_bet) FROM session_log WHERE closed_at >= ? AND closed_at < ?

-- 3) carried_in: 창 안에서 마감된 세션에 속하지만, 스핀 시각은 창 밖
SELECT SUM(d.bet_amount) FROM play_log d JOIN session_log g ON d.session_id = g.session_id
WHERE g.closed_at >= ? AND g.closed_at < ?
  AND (d.played_at < ? OR d.played_at >= ?)

-- 4) carried_out: 스핀은 창 안인데, 세션이 진행 중이거나 창 이후에 마감
SELECT SUM(d.bet_amount) FROM play_log d JOIN session_log g ON d.session_id = g.session_id
WHERE d.played_at >= ? AND d.played_at < ?
  AND (g.closed_at IS NULL OR g.closed_at >= ?)
```

코드에서는 지표(베팅, 지급, 스핀 수)를 한 쿼리에서 같이 더합니다. 스핀 수는 `SUM(1)`로 셉니다. 행마다 1을 더하면 개수가 되기 때문입니다.

**왜 창을 `>= start AND < end`로 잡았나**: 끝 시각을 포함하면(`<=`) 정확히 13:00:00에 찍힌 건이 이번 창과 다음 창에 둘 다 들어갑니다. 창을 이어 붙였을 때 겹치거나 빠지는 건이 없게 하려고 시작은 포함, 끝은 제외로 통일했습니다. 이걸 `<=`로 바꾸면 테스트가 실패하는 것도 확인했습니다.

**테이블 이름을 f-string으로 넣는 이유**: SQL에서 값(시각)은 `?`로 바인딩할 수 있지만 테이블 이름이나 컬럼 이름은 바인딩이 안 됩니다. 그래서 이름은 문자열로 넣되, 그 이름은 `scenarios.py`에 코드로 고정된 값에서만 오게 했습니다. 사용자가 입력한 값이 SQL 문장에 들어가는 경로는 없습니다. 시각 같은 값은 전부 `?` 바인딩입니다.

### 드릴다운 5개

| 함수 | 찾는 것 | 미설명 차이에 주는 영향 |
|---|---|---|
| `_check_group_mismatch` | 세션 합계와 그 세션에 속한 스핀 전체 합이 다른 세션 | +(세션 합계 - 스핀 합) |
| `_check_orphans` | 창 안의 스핀인데 소속 세션 행이 아예 없음 | -(그 스핀 금액) |
| `_check_late_rows` | 창 안의 스핀인데 소속 세션은 창 시작 전에 이미 마감 | -(그 스핀 금액) |
| `_check_dup_keys` | 같은 play_id가 두 번 이상 | 금액은 합계 불일치에 반영됨 |
| `_check_time_inversion` | 세션 기간 밖 시각으로 찍힌 스핀 | 없음 (WARN) |

`_check_group_mismatch`에서 스핀 합을 구할 때는 시각과 상관없이 그 세션의 스핀을 전부 더합니다. 여기서 보려는 건 시간 창이 아니라 "세션 단위로 장부가 맞느냐"이기 때문입니다.

### 등식 검증 (closure check)

수학적으로 아래가 항상 성립해야 합니다.

```
미설명 차이 = 합계 불일치 합 - 마감 이후 기록 합 - 집계 누락 합
```

`MetricResult.closure_ok`가 이걸 확인합니다. 만약 안 맞으면 엔진이 찾지 못한 종류의 문제가 있다는 뜻입니다. 그때는 "정상"이나 "결함 후보"가 아니라 "검증 불가"로 판정합니다. 도구가 자기가 놓친 걸 정상이라고 말하는 상황을 막는 장치입니다.

면접에서 이렇게 말하면 됩니다: "결함을 찾은 금액의 합이 전체 차이와 1원 단위까지 맞는지를 도구가 스스로 확인합니다. 안 맞으면 결과를 내지 않습니다."

### 허용 오차

`Metric.tolerance_per_row`. 게임은 0이라 1원이라도 다르면 결함입니다. 결제 수수료는 건당 1원입니다. 건별로 절사한 수수료의 합과 배치 합계에서 한 번 절사한 수수료는 정상이어도 최대 (건수 - 1)원 차이가 나기 때문입니다. 허용 오차 내 차이는 `mismatch_tolerated`에 따로 모아서 리포트에 "허용 오차 내" 열로 보여줍니다. 숨기지 않고 얼마가 정책 차이로 설명됐는지 보이게 했습니다.

## 4. 데이터 생성기 (`recon/generate.py`)

### 게임
유저 200명이 3~4일 동안 세션을 여러 번 합니다. 세션 길이는 5분 ~ 2시간, 스핀 간격은 20초 ~ 90초, 세션 사이 쉬는 시간은 30분 ~ 10시간입니다. 기준 시각(now)에 아직 안 끝난 세션은 `closed_at`을 NULL로 남깁니다. 실제로 대조하는 순간에도 진행 중인 세션이 있기 때문입니다.

### 결제
가맹점 30곳, 하루 1개 배치, 매일 23시 컷오프. 그래서 23시 ~ 24시 승인 건은 다음 날 배치로 넘어갑니다. 자정 기준으로 하루를 자르면 경계 효과가 생기는 구조입니다. 시간대별 거래량을 다르게 두었고(밤에 적고 저녁에 많음), 3% 확률로 같은 배치 안에서 취소(음수 행)가 생깁니다.

### 결함 주입
결함 주입 함수는 무엇을 어디에 심었는지(정답지)를 돌려줍니다. 테스트는 엔진이 찾은 목록과 정답지가 정확히 같은지 봅니다. 하나라도 놓치면 실패, 정답지에 없는 걸 잡아도(오탐) 실패입니다.

결함끼리 같은 세션을 건드리지 않게 하고, 창 경계 6시간 안쪽 세션은 피합니다. 정답지를 깔끔하게 유지하기 위해서입니다.

## 5. 릴리즈 게이트 (`gate/gate.py`)

판정 순서

1. **입력 검증**: pass + fail + blocked + na가 total과 다르거나, 모르는 심각도나 상태가 있거나, ID가 중복이면 판정하지 않고 종료 코드 3. 입력이 틀렸는데 판정을 내리면 틀린 판정이 나오기 때문입니다
2. **TC 통과율**: 전체 95% 미만이면 차단. 금전성 영역(결제, 재화, DB 정합성)은 100% 미만이면 차단, 수행 못 한 TC가 1건이라도 있으면 차단. 일반 카테고리는 95% 미만이면 조건부
3. **N/A 비율**: 10% 넘으면 조건부. 제외한 이유를 확인하라는 뜻입니다
4. **결함 분류**: 매트릭스로 차단, 조건부, 출시 후 대응을 정합니다. 금전성 영역 결함은 심각도를 한 단계 올립니다. 조건부인데 수정 계획이 없으면 차단입니다
5. **결함 등록 누락**: 실패 TC가 있는데 그 카테고리에 열린 결함이 없으면 조건부

하나라도 차단이면 NO-GO, 차단은 없고 조건이 있으면 CONDITIONAL GO, 둘 다 없으면 GO.

**규칙을 JSON 파일로 뺀 이유**: 기준을 바꿀 때마다 코드를 고치면 개발자만 바꿀 수 있고, 무엇이 언제 바뀌었는지 추적하기 어렵습니다. 파일로 빼면 QA가 직접 바꿀 수 있고 변경 이력이 남습니다.

**Fixed를 열린 상태로 보는 이유**: 개발자가 수정했다고 한 것과 QA가 재검증해서 확인한 것은 다릅니다. Verified나 Closed가 되기 전까지는 출시 판정에서 열린 결함입니다.

**Deferred(보류)를 판정에서 빼지 않는 이유**: 보류를 누르면 판정에서 빠진다면, 차단 결함도 보류 처리로 우회할 수 있습니다. 담당자 판단이 아니라 합의된 기준으로 결정한다는 원칙을 코드로 지킨 부분입니다.

## 6. 테스트 전략

세 단계로 나눴습니다.

1. **손계산 테스트** (`test_recon_oracle.py`): 정답을 사람이 계산할 수 있는 작은 데이터. 엔진이 내는 숫자가 정확히 맞는지 봅니다
2. **대량 데이터 테스트** (`test_recon_generated.py`): 정상 데이터에서 1시간, 3시간, 1일, 3일 창 어디서도 오탐이 없는지. 시드를 바꿔가며 심은 결함을 정확히 찾는지
3. **뮤테이션 테스트** (`tools/mutation_check.py`): 코드에 버그를 일부러 심어서 테스트가 실패하는지. 테스트 자체를 검증합니다

경계값 테스트도 넣었습니다. 통과율 정확히 95%는 통과, 수수료 오차가 허용치와 같으면 통과하고 1원 넘으면 결함.

## 7. 예상 질문과 답

**Q. 이거 직접 짰어요?**
AI 코딩 도구(Claude)로 작성했습니다. 문제 정의와 판정 기준은 실무에서 제가 하던 방식에서 가져왔고, 코드는 AI가 짰고, 결과는 제가 테스트로 검증했습니다. 검증하면서 실제로 고친 것들은 검증 기록 문서에 남겨 두었습니다. 공고에 AI가 생성한 산출물을 검증하고 책임지는 역량을 적어 주셨는데, 이 프로젝트가 그 과정 그대로입니다.

**Q. AI가 짠 코드를 어떻게 믿어요?**
세 가지로 확인했습니다. 손으로 계산한 정답과 맞추는 테스트, 결함을 심어서 정확히 그것만 잡는지 보는 테스트, 그리고 코드에 일부러 버그를 심어서 테스트가 그걸 잡는지 보는 뮤테이션 테스트입니다. 테스트 70개가 처음부터 다 통과해서 오히려 테스트가 약한 게 아닌지 의심했고, 그래서 뮤테이션 테스트를 추가했습니다. 9개 심어서 9개 다 잡혔습니다.

**Q. 실무에서는 3일 창으로 했다면서, 그게 틀렸다는 건가요?**
틀렸다기보다 한계가 있었습니다. 3일로 넓히면 경계 효과가 0.1% 수준으로 줄어서 실무적으로는 판단이 가능했습니다. 다만 남은 차이가 잔여분 수준이라는 건 사람이 판단한 것이고, 그 잔여분 안에 작은 결함이 숨을 수 있습니다. 경계 효과를 정확히 계산해서 빼면 그 판단이 필요 없어집니다.

**Q. 실제 DB에서는 session_id가 스핀 로그에 없으면요?**
그게 이 도구의 가장 큰 전제입니다. 소속 세션 ID가 없으면 유저 ID와 시각 범위로 소속을 추정해야 하는데, 세션이 겹치거나 시각이 어긋나면 정확도가 떨어집니다. 실제 환경에 붙인다면 먼저 그 연결 키가 있는지부터 확인하겠습니다.

**Q. 데이터가 수억 건이면요?**
지금은 SQLite에 20만 건이라 한 번에 돕니다. 수억 건이면 날짜 파티션 단위로 나눠 돌리고, 세션 합계 비교는 마감 시각 인덱스로 범위를 좁혀야 합니다. 지금도 합계 불일치 검사는 창 안에서 마감된 세션에 속한 스핀만 골라서 묶도록 되어 있습니다. 운영 DB에 직접 돌리면 부하가 생기니 복제본이나 분석용 DB에서 돌리는 게 맞습니다.

**Q. 왜 Python, 왜 SQLite?**
설치 없이 어디서나 돌아가게 하려고 표준 라이브러리만 썼습니다. 엔진이 하는 일은 대부분 SQL이라 MySQL로 옮길 때 바뀌는 건 접속 부분과 날짜 비교 정도입니다.

**Q. 허용 오차는 왜 지표마다 다르게 뒀어요?**
금액과 건수는 1원, 1건이라도 다르면 결함입니다. 수수료는 건별 절사와 합계 절사 정책 차이 때문에 정상이어도 원 단위 차이가 납니다. 그걸 결함으로 잡으면 매일 오탐이 나서 아무도 리포트를 안 보게 됩니다. 반대로 허용 오차를 크게 잡으면 진짜 결함이 숨습니다. 그래서 정책상 날 수 있는 최대치(건당 1원)로 정했습니다. 그리고 처음엔 절사 차이가 늘 양수라 한쪽 방향만 허용할까 했는데, 취소 건은 반대로 절사되는 걸 확인하고 양방향으로 뒀습니다.

**Q. 게이트에서 금전성 영역을 100%로 잡은 건 너무 엄격하지 않아요?**
금액이 걸린 결함은 출시 후에 고쳐도 이미 잘못 지급된 금액이 남습니다. 회수하거나 보상해야 하고 고객 신뢰 문제가 됩니다. 그래서 다른 영역과 기준을 다르게 뒀습니다. 다만 기준은 rules.json에 있어서 조직이 합의하면 바꿀 수 있습니다.

**Q. CI/CD에는 어떻게 붙여요?**
두 도구 다 판정을 종료 코드로 돌려줍니다. 파이프라인에서 종료 코드가 2 이상이면 배포 단계로 넘어가지 않게 하면 됩니다. 저장소에 GitHub Actions 예시를 넣어 두었습니다. 도구 자체 테스트를 먼저 돌리게 했는데, 도구가 틀리면 판정도 믿을 수 없기 때문입니다.

**Q. 제일 어려웠던 부분은?**
창을 어디서 자르냐에 따라 같은 건이 WARN이 되기도 하고 FAIL이 되기도 하는 걸 발견했을 때입니다. 버그인지 맞는 동작인지 판단하려고 손계산 데이터로 재현했고, 뒤 창 입장에서는 실제로 설명할 수 없는 금액이 생긴 게 맞아서 정상 동작으로 결론 내리고 테스트로 고정했습니다.

**Q. 더 개선한다면?**
세 가지입니다. 실제 MySQL 연결 어댑터, 창별 결과를 날짜별로 쌓아서 추세를 보는 대시보드, 그리고 게이트에서 TC와 결함을 ID로 연결해 카테고리가 아니라 TC 단위로 결함 등록 누락을 잡는 것입니다.

## 9. API 하네스 (`apiqa/`)

### 30초 설명
연습용 메시지 서버를 띄우고, 그 API를 코드로 직접 호출해서 인증, 권한, 응답 형식, 경계값, 재전송, 페이지 조회, 동시 요청을 검증합니다. 그리고 서버에 결함을 일부러 하나씩 심어, 하네스가 그 결함을 실제로 잡는지까지 확인합니다.

### 구성
- `server.py`: 검증 대상 서버. `bug` 인자로 결함 7종 중 하나를 켤 수 있습니다
- `client.py`: `ApiClient`는 요청을 보내고 상태 코드, 헤더, 본문을 돌려줍니다. 4xx, 5xx도 예외로 터뜨리지 않고 그대로 돌려줘서 테스트가 오류 응답을 검증할 수 있습니다. `check_schema`는 응답 필드와 타입이 계약과 다른 점을 목록으로 돌려줍니다
- `tests/test_api_contract.py`: 테스트마다 새 서버를 띄웁니다. 앞 테스트에서 보낸 메시지가 뒤 테스트에 섞이지 않게 하기 위해서입니다
- `tools/api_fault_check.py`: `APIQA_BUG` 환경 변수로 결함을 켠 서버에 대해 같은 테스트를 돌리고, 실패하면 잡힌 것으로 봅니다

### 예상 질문과 답
**멱등성은 왜 검증했나요?**
네트워크가 끊겨 클라이언트가 같은 요청을 다시 보내면, 서버가 그걸 새 요청으로 처리해 메시지나 결제가 두 번 생길 수 있습니다. 같은 키로 두 번, 그리고 동시에 열 번 보내서 1건만 생기는지 봤습니다.

**페이지 조회는 어떻게 검증했나요?**
25건을 보내고 limit 1, 7, 25, 100으로 커서를 끝까지 따라가 모은 결과가 보낸 순서와 정확히 같은지 봤습니다. 빠짐, 중복, 순서가 한 번에 확인됩니다. limit이 전체 건수의 약수가 아닌 7을 넣은 이유는 마지막 페이지가 꽉 차지 않는 경우를 보기 위해서입니다.

**1000자, 1001자를 둘 다 넣은 이유는요?**
경계값 결함은 기준값 바로 위와 바로 위의 한 칸에서 납니다. 1000자 허용, 1001자 거부를 같이 봐야 `>`와 `>=`를 잘못 쓴 결함이 잡힙니다. 실제로 이 결함을 심었을 때 이 테스트가 잡았습니다.

**정상 서버에서 테스트가 실패한 적이 있나요?**
동시 전송 40건 테스트가 처음에 연결 끊김으로 실패했습니다. 서버의 연결 대기열 기본값이 5라 동시에 몰린 요청이 거부된 것이었고, 서버 로직 결함이 아니라 환경 문제였습니다. 그 뒤로 결함 주입 전에 정상 서버 통과를 먼저 확인하게 했습니다.

**실제 서비스에 쓰려면 무엇을 바꿔야 하나요?**
ApiClient의 주소와 토큰을 실제 환경 값으로 바꾸면 호출은 그대로 됩니다. 다만 테스트마다 서버를 새로 띄우는 방식은 쓸 수 없으니, 테스트용 계정과 대화방을 만들고 끝나면 정리하는 준비 단계를 따로 만들어야 합니다.
