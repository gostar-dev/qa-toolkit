# AI 활용 및 검증 기록

## 역할 분담

| 단계 | 누가 | 내용 |
|---|---|---|
| 문제 정의 | 본인 | 실무에서 3시간 창 대조가 흔들렸던 문제, 3일 창으로 넓혀 판단했던 방식의 한계 |
| 판정 기준 | 본인 | 결함 2축 기준표, 금전성 영역 100% 통과 원칙, 재현 불가로 닫지 않는 원칙, 설명 안 되는 차이는 크기와 관계없이 결함 후보 |
| 코드 작성 | AI 코딩 도구 (Claude) | 엔진, 생성기, 리포트, CLI, 테스트 초안 |
| 검증 | 본인 + 테스트 | 아래 기록 |

기준은 사람이 정하고, 구현은 AI에게 맡기고, AI가 만든 결과는 테스트로 검증한다는 원칙으로 진행했습니다.

## 검증하면서 발견한 문제와 조치

### 1. 테스트 70개가 첫 실행에 전부 통과함
전부 통과했다는 건 코드가 맞다는 뜻일 수도 있지만, 테스트가 약하다는 뜻일 수도 있습니다. 그래서 코드에 일부러 버그를 9개 심고 테스트가 실패하는지 확인했습니다 (`tools/mutation_check.py`).

심은 버그: 경계 효과 계산에서 한 항목 누락, 진행 중인 세션 누락, 허용 오차 경계값 `<=`를 `<`로, 창 끝 시각 포함, 중복 보고 방지 제거, 금전성 영역 심각도 상향 제거, 통과율 경계값, 재검증 전 결함을 종료로 취급, 결함 미등록 검사 제거.

결과: 9개 모두 테스트가 잡음. 이 스크립트는 저장소에 남겨서 테스트를 고칠 때마다 다시 돌릴 수 있게 했습니다.

### 2. 생성기와 엔진이 같은 착각을 공유할 위험
생성기와 엔진을 같은 도구가 만들었기 때문에, 둘 다 같은 방식으로 틀리면 생성기 데이터 기반 테스트는 통과해 버립니다. 그래서 7건짜리 데이터를 직접 만들고 carried_in 100, carried_out 110, 원시 차이 -10을 손으로 계산해서 엔진 결과와 비교하는 테스트를 따로 두었습니다 (`tests/test_recon_oracle.py`).

### 3. 수수료 허용 오차를 한쪽 방향으로만 둘지 검토
정상 데이터 120개 배치에서 배치 수수료와 건별 수수료 합의 차이를 뽑아보니 전부 양수(19원 ~ 125원)였습니다. 그래서 음수 차이는 결함으로 보도록 한쪽 방향만 허용하는 게 더 엄격하지 않을까 검토했습니다.

계산해 보면 취소 건은 음수 금액이라 절사 방향이 반대가 되고, 취소가 많은 배치에서는 음수 차이가 날 수 있습니다. 생성 데이터에서는 취소 비율이 3%라 안 보였을 뿐입니다. 데이터에 안 보였다고 규칙을 좁히면 실제 환경에서 오탐이 납니다. 양방향 허용을 유지했습니다.

### 4. 한 건이 두 번 보고되는 구조
'마감 이후 기록' 건은 정의상 세션 마감 시각보다 늦게 찍힌 건이라 '시간 역전' 검사에도 같이 걸립니다. 그대로 두면 한 건이 FAIL과 WARN으로 두 번 보고되어 개발팀에 혼란을 줍니다. 이미 마감 이후 기록으로 잡힌 건은 시간 역전 목록에서 빼도록 했고, 이게 깨지면 실패하는 테스트를 넣었습니다.

### 5. 창을 자르는 위치에 따라 판정이 바뀌는 경우
세션 마감 5분 뒤에 찍힌 건은 3시간 창 하나 안에 다 들어가면 금액 영향이 없어 WARN입니다. 그런데 창 경계가 마감 시각과 그 건 사이에 오면, 뒤 창에서는 이미 마감된 세션에 금액이 늦게 들어온 것이 되어 FAIL이 됩니다.

버그인지 정상 동작인지 판단하기 위해 손계산 데이터로 재현했습니다. 뒤 창 입장에서는 실제로 설명할 수 없는 금액이 생긴 것이 맞으므로 정상 동작으로 판단했고, 이 동작을 테스트로 고정했습니다 (`test_time_inversion_crossing_window_edge_becomes_late_row`). 창을 잘게 나눌수록 시각 기록 문제에 더 민감해진다는 뜻이기도 합니다.

### 6. 배치 하나의 누락이 두 창에 나눠서 보고됨
결제 배치는 전날 23시부터 당일 23시까지라 일별 창(0시 ~ 24시) 두 개에 걸칩니다. 배치 하나가 통째로 누락되면 앞 창에서 23시 이후 승인분이, 뒤 창에서 나머지가 따로 보고됩니다. 같은 원인이지만 창 단위로는 각각 맞는 보고이므로 그대로 두고, 리포트를 읽을 때 같은 대상 ID로 묶어서 보면 된다는 점을 기록했습니다.

### 7. 리포트에 내부 변수 이름이 노출됨
결함 상세에 `bet`, `win`, `spins` 같은 코드 내부 이름이 그대로 찍혀서, 개발팀이 아닌 사람이 읽기 어려웠습니다. 표시 이름(베팅 합계, 지급 합계, 스핀 수)으로 바꿨습니다.

### 8. 결함 주입기가 특정 데이터에서 멈출 수 있는 경로
취소 미반영 결함을 심을 때 가맹점 수수료율을 10만 원 초과 거래 하나로 추정하게 되어 있었습니다. 그런 거래가 없는 가맹점이 뽑히면 조회 결과가 비어 실행이 멈춥니다. 코드를 읽다가 발견했고, 가장 큰 거래로 추정하도록 바꿨습니다.

### 9. 정상 서버에서 동시 전송 테스트가 실패함
결함을 심지 않은 서버인데 40건 동시 전송 테스트가 연결 끊김으로 실패했습니다. 서버 로직의 결함인지 테스트 환경 문제인지부터 나눠 봤고, 원인은 서버의 연결 대기열 기본값(5)이었습니다. 동시에 몰린 요청이 대기열을 넘어 거부된 것입니다. 대기열을 늘리고 같은 테스트를 3번 반복해 모두 통과하는지 확인했습니다. 이 일 때문에 결함 주입 스크립트는 정상 서버에서 전부 통과하는지 먼저 확인하고, 아니면 결함 주입을 시작하지 않게 했습니다. 정상 서버에서 이미 실패하면 결함을 잡았다는 결과도 믿을 수 없기 때문입니다.

### 10. 동시성 결함은 운에 따라 안 잡힐 수 있음
순번 발급에 잠금이 없는 결함은 요청이 실제로 겹쳐야 드러납니다. 한 번 잡혔다고 끝내지 않고 같은 결함으로 5번 반복 실행해 5번 모두 잡히는 것을 확인했습니다. 그래도 타이밍에 의존하는 테스트라는 점은 README 한계에 적었습니다.

## AI가 만든 결과를 볼 때 기준

1. 테스트가 통과했다는 사실보다 테스트가 무엇을 확인하는지를 먼저 본다
2. 정답을 아는 작은 데이터로 한 번은 손으로 맞춰 본다
3. 데이터에 안 보였다는 이유로 규칙을 좁히지 않는다
4. 도구가 스스로 결과를 점검할 수 있게 만든다 (이 도구에서는 등식 검증)
5. 이해하지 못한 코드는 쓰지 않는다
